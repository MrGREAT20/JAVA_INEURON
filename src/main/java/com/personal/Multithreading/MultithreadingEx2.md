# Creating Threads by Extending `Thread` in Java

On a single thread, unrelated tasks still have to wait for each other. By extending `Thread` and overriding `run()`, each task gets its own thread, so the tasks run at the same time and the total time drops to roughly that of the slowest task.

## Key Features
* **Sequential bottleneck:** In the first half, three tasks run one after another on `main`: 3 tasks x 3 sleeps x 2 s = about 18 seconds.
* **`extends Thread`:** Put the task in an overridden `run()`, create the object, then call `start()`.
* **`start()` creates the thread:** `start()` asks the JVM to create a new OS thread, and that new thread calls `run()`. Calling `run()` yourself is an ordinary method call on the current thread.
* **Parallel speed-up:** In the second half, the three threads sleep at the same time, so the work takes about 6 seconds instead of 18 (the whole run measured 24 s = 18 + 6).
* **`main` can end first:** `main` returns right after the three `start()` calls. The JVM keeps running until every **non-daemon** thread has finished.
* **Checked exception in `run()`:** `run()` cannot declare `throws InterruptedException`, so `Thread.sleep()` must be wrapped in `try/catch` inside it.

## Comparison: `start()` vs `run()`

| `start()` | `run()` |
| --- | --- |
| Creates a new call stack / OS thread | Runs on the current thread |
| Returns at once; work happens in parallel | Blocks until the method finishes |
| Allowed only once per `Thread` object (`IllegalThreadStateException` otherwise) | Can be called any number of times (plain method) |
| `Thread.currentThread().getName()` inside is e.g. `Thread-0` | `Thread.currentThread().getName()` inside is `main` |

## Day-to-Day Points for Experienced Developers

* **Use an `ExecutorService` instead of raw `new Thread()`:** Creating a platform thread per task is expensive and unbounded. A pool reuses threads and caps concurrency. Since Java 19, `ExecutorService` is `AutoCloseable`, and `close()` waits for submitted tasks.
  ```java
  try (ExecutorService ex = Executors.newFixedThreadPool(3)) {
      ex.submit(() -> doBanking());
      ex.submit(() -> doPrinting());
  } // waits here for the tasks
  ```
* **Size pools by workload:** CPU-bound work: about `Runtime.getRuntime().availableProcessors()` threads. Blocking I/O work: use virtual threads (Java 21+) instead of guessing a large pool size.
* **Shut down executors you create without try-with-resources:** Call `shutdown()` then `awaitTermination(...)`; otherwise the non-daemon pool threads keep the JVM alive after `main` ends.
* **Handle `InterruptedException` properly:** Do not just `printStackTrace()`, as these examples do. Interruption is how code asks a thread to stop (`future.cancel(true)`, `executor.shutdownNow()`). Either rethrow it or restore the flag and exit.
  ```java
  catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }
  ```
* **Do not catch plain `Exception` around `sleep()`:** It hides the interrupt and swallows real bugs. Catch `InterruptedException` specifically.
* **Calling `run()` instead of `start()` is a classic code-review catch:** It compiles, works, and silently makes everything sequential. Watch for it in reviews and tests that "pass but are slow".
* **`System.out.println` is synchronized:** Each line is printed whole, but heavy logging from many threads serializes them on that lock. In production use an async logger, not `System.out`.

* **Copy-paste bug in `Work3` (~line 82):** The "Calculations" thread also prints `"Banking ....."` on each loop iteration. This is why "Banking ....." appears 6 times in the second half instead of 3.
